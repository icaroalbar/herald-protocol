## Sumário

Este documento especifica o **Herald Protocol**, um protocolo aberto, construído sobre
HTTP, que permite a aplicações web identificar agentes de IA (assistentes, crawlers de
treinamento, agentes autônomos de navegação, etc.), negociar a melhor forma de entregar
conteúdo, declarar e aplicar políticas de acesso, e gerar observabilidade sobre o consumo
desses agentes — sem alterar o conteúdo servido a humanos.

As palavras-chave "MUST", "MUST NOT", "SHOULD", "SHOULD NOT" e "MAY" neste documento devem
ser interpretadas conforme RFC 2119.

---

## 1. Motivação

A web foi desenhada para humanos operando navegadores. Hoje, uma fração crescente do
tráfego HTTP é originada por agentes de IA: crawlers de treinamento de modelos, assistentes
que navegam em nome de um usuário, agentes autônomos que executam tarefas, e bots de
indexação para busca semântica.

Não existe hoje um padrão que permita a um servidor:

1. Identificar de forma confiável que a requisição vem de um agente de IA, e qual agente.
2. Negociar com esse agente a melhor forma de entregar a informação (ex: JSON estruturado
   em vez de HTML renderizado).
3. Declarar políticas — o que pode ser lido, usado para treinamento, redistribuído,
   monetizado, e sob qual limite de taxa.
4. Medir e observar esse consumo de forma agregada (analytics por agente).

O Herald Protocol resolve isso como uma camada de convenções sobre HTTP: headers, um
endpoint de descoberta bem conhecido, e um formato de negociação — sem quebrar
compatibilidade com clientes HTTP que não conhecem o protocolo.

## 2. Terminologia

- **Agente (Agent)**: qualquer cliente automatizado que não seja um navegador operado
  interativamente por um humano — inclui crawlers, assistentes de IA, agentes autônomos.
- **Origem (Origin)**: o servidor/aplicação que expõe conteúdo e implementa o Herald
  Protocol.
- **Gateway**: componente (middleware ou proxy reverso) que implementa o Herald Protocol
  na Origem.
- **Policy Engine**: componente que avalia políticas de acesso para uma dada combinação
  agente/recurso/intenção.
- **Capacidade (Capability)**: uma forma de representação ou funcionalidade que um agente
  ou origem suporta (ex: `structured-json`, `markdown`, `streaming`).
- **Intenção (Intent)**: a finalidade declarada do acesso (ex: `read`, `train`,
  `redistribute`, `monetize`).
- **Documento de Descoberta (Discovery Document)**: o JSON servido em
  `/.well-known/herald` descrevendo capacidades e políticas da origem.

## 3. Princípios de Design

1. **Compatibilidade retroativa**: um cliente HTTP que ignora o Herald Protocol recebe
   exatamente o comportamento atual — o protocolo é aditivo.
2. **Conteúdo inalterado, entrega diferenciada**: o Herald Protocol não permite que a
   informação fornecida a um agente seja materialmente diferente daquela fornecida a um
   humano para o mesmo recurso — apenas o formato/estrutura de entrega pode variar (ver §7).
3. **Opt-in e descoberta explícita**: a negociação depende de headers explícitos; não há
   fingerprinting adivinhado como mecanismo primário de identificação.
4. **Extensibilidade**: novos campos, capacidades e políticas devem poder ser adicionados
   sem quebrar implementações existentes (ver §9).

## 4. Identificação de Agentes

### 4.1 Header `Herald-Agent-Id`

Um agente que implementa o Herald Protocol DEVE enviar o header `Herald-Agent-Id`
identificando-se de forma estável:

```
Herald-Agent-Id: anthropic-claude/1.0
```

Formato: `<vendor>-<produto>/<versão>`, minúsculo, ASCII, sem espaços.

### 4.2 Header `Herald-Agent-Type`

Classifica a natureza do acesso:

```
Herald-Agent-Type: assistant | crawler | autonomous | search-index
```

| Valor | Descrição |
|---|---|
| `assistant` | Agente conversacional atuando em nome direto de um usuário em tempo real |
| `crawler` | Coleta em lote, tipicamente para indexação ou treinamento |
| `autonomous` | Agente executando tarefas multi-etapa sem supervisão humana síncrona |
| `search-index` | Indexação para busca (tradicional ou semântica) |

### 4.3 Fallback via User-Agent

Para compatibilidade com agentes que ainda não implementam o Herald Protocol, o Gateway
DEVE também inspecionar o header `User-Agent` padrão contra uma lista de padrões conhecidos
(ex. `GPTBot`, `ClaudeBot`, `PerplexityBot`, `CCBot`). Quando um agente é identificado
apenas por essa via, o Gateway MUST marcar a identificação como `unverified` internamente
e nas métricas — ela não deve ser tratada com o mesmo nível de confiança que
`Herald-Agent-Id`.

### 4.4 Verificação de Identidade (opcional, recomendado)

Origens que aplicam políticas restritivas (ex. bloqueio de treinamento) SHOULD suportar
verificação criptográfica via assinatura HTTP Message Signatures (RFC 9421) sobre o header
`Herald-Agent-Id`, permitindo confirmar que a requisição realmente se origina do agente
declarado. O mecanismo de emissão de chaves está fora do escopo deste RFC.

## 5. Negociação de Capacidades e Formato

### 5.1 Header de requisição `Herald-Accept-Capabilities`

O agente declara o que é capaz de consumir, em ordem de preferência:

```
Herald-Accept-Capabilities: structured-json;q=1.0, markdown;q=0.8, html;q=0.3
```

Sintaxe idêntica ao `Accept` HTTP padrão (RFC 9110 §12.5.1), com `q` de 0 a 1.

### 5.2 Header de resposta `Herald-Content-Format`

A origem informa qual formato foi de fato usado na resposta:

```
Herald-Content-Format: structured-json
```

### 5.3 Header `Vary`

Toda resposta cujo corpo varia conforme negociação Herald MUST incluir:

```
Vary: Herald-Agent-Id, Herald-Accept-Capabilities
```

Isso garante comportamento correto de caches HTTP intermediários.

### 5.4 Fluxo de negociação

1. Agente envia requisição com `Herald-Agent-Id`, `Herald-Agent-Type`,
   `Herald-Accept-Capabilities`.
2. Gateway consulta o Policy Engine para o par (agente, recurso, intenção).
3. Se permitido, Gateway seleciona a capacidade de maior `q` que a origem também suporta
   para aquele recurso.
4. Resposta é servida com `Herald-Content-Format` e `Vary` apropriados.
5. Se nenhuma capacidade em comum existir, a origem MUST retornar a representação padrão
   (HTML) — nunca falhar a requisição por incompatibilidade de formato.

## 6. Endpoint de Descoberta `/.well-known/herald`

Toda origem compatível com o Herald Protocol MUST expor `GET /.well-known/herald`,
retornando `application/json`, sem exigir autenticação.

### 6.1 Schema (resumo)

```json
{
  "herald_version": "1.0",
  "origin": "https://example.com",
  "capabilities": ["structured-json", "markdown", "html"],
  "endpoints": {
    "structured": "https://example.com/api/herald/{path}"
  },
  "policies": {
    "default": {
      "read": "allow",
      "train": "deny",
      "redistribute": "deny",
      "monetize": "not-applicable",
      "rate_limit": { "requests": 60, "window_seconds": 60 }
    },
    "by_agent_type": {
      "search-index": { "read": "allow", "train": "deny" },
      "crawler": { "read": "allow", "train": "ask", "rate_limit": { "requests": 10, "window_seconds": 60 } }
    }
  },
  "analytics": {
    "reporting": "aggregate",
    "contact": "mailto:agents@example.com"
  },
  "extensions": {}
}
```

Schema JSON completo (JSON Schema Draft 2020-12) em
[`well-known-herald.schema.json`](./well-known-herald.schema.json), com referência
detalhada de todos os headers em [`HEADERS.md`](./HEADERS.md).

### 6.2 Cache

A resposta SHOULD incluir `Cache-Control: max-age=3600` ou superior. Agentes SHOULD
armazenar em cache o documento de descoberta e revalidar periodicamente em vez de
consultá-lo a cada requisição.

## 7. Resposta Diferenciada Sem Alterar Conteúdo

Este é um princípio normativo central do Herald Protocol (ver §3.2).

- A origem MAY servir a um agente uma representação estruturalmente diferente do mesmo
  recurso (ex. JSON em vez de HTML renderizado, remoção de markup de apresentação,
  inclusão de metadados adicionais como autoria e data).
- A origem MUST NOT usar a negociação Herald para omitir, resumir de forma enganosa, ou
  alterar fatos/informação substantiva presente na versão servida a humanos para o mesmo
  recurso e mesma janela de tempo.
- Alterações permitidas: formato de serialização, estrutura de navegação, presença de
  elementos de UI (menus, anúncios, banners de cookie), nível de detalhe de metadados
  técnicos (ex: schema.org).
- Alterações não permitidas: remoção de seções de conteúdo editorial, alteração de preços,
  termos, ou dados factuais apresentados ao agente de forma diferente do que seria
  apresentado a um humano.

Esse princípio existe para que o Herald Protocol não se torne um mecanismo de cloaking
(prática já penalizada por motores de busca) e para preservar confiança entre origens e
agentes.

## 8. Policy Engine

### 8.1 Intenções (Intents)

| Intent | Significado |
|---|---|
| `read` | Acesso de leitura pontual em nome de um usuário/tarefa |
| `train` | Uso do conteúdo para treinamento de modelos |
| `redistribute` | Republicação do conteúdo, total ou parcial, para terceiros |
| `monetize` | Uso comercial direto do conteúdo por terceiro |
| `rate_limit` | Não é uma intenção de acesso, mas uma política aplicada transversalmente |

### 8.2 Valores de política

Cada intent (exceto `rate_limit`) resolve para um de: `allow`, `deny`, `ask`,
`not-applicable`.

- `allow`: acesso concedido incondicionalmente.
- `deny`: acesso negado; Gateway MUST responder `403` com corpo explicando a política
  violada (ver §8.4).
- `ask`: acesso requer aprovação — fora de banda (ex. acordo comercial negociado
  manualmente) ou automatizável via pagamento. Em ambos os casos o Gateway MUST responder
  `402`. Quando o `ask` é resolvível por pagamento automatizado, a implementação de
  referência usa o fluxo x402 descrito em [MONETIZATION.md](./MONETIZATION.md): a resposta
  `402` carrega um header `Payment-Required`; o agente reenvia a requisição com
  `Payment-Signature`; a origem responde com `Payment-Response` e, se liquidado, trata a
  requisição como `allow` a partir daí. Essa extensão é estritamente opcional e aditiva —
  um Gateway que não a implementa continua respondendo `402` sem esses headers, o que
  permanece uma resposta válida para o intent `ask`.
- `not-applicable`: a intenção não se aplica ao tipo de recurso.

### 8.3 Resolução de política

A resolução de política para uma requisição segue ordem de precedência (mais específico
vence):

1. Política por recurso (declarada via header `Herald-Resource-Policy` na origem, ou
   configuração de rota no Gateway).
2. Política por `Herald-Agent-Id` específico (allowlist/denylist nomeada).
3. Política por `Herald-Agent-Type`.
4. Política `default` do documento de descoberta.

### 8.4 Header de resposta `Herald-Policy-Decision`

Toda resposta processada pelo Policy Engine MUST incluir:

```
Herald-Policy-Decision: intent=train; result=deny; rule=by_agent_type.crawler
```

Isso permite que o agente entenda exatamente qual regra foi aplicada, sem ambiguidade.

### 8.5 Rate limiting

Rate limit é expresso em requisições por janela de tempo. Ao exceder, o Gateway MUST
responder `429 Too Many Requests` com header `Retry-After`, conforme RFC 9110.

## 9. Analytics e Observabilidade

### 9.1 Métricas mínimas

Um Gateway compatível com o Herald Protocol SHOULD coletar, por agente:

- Contagem de requisições, por `Herald-Agent-Id` e `Herald-Agent-Type`.
- Contagem de decisões do Policy Engine por resultado (`allow`/`deny`/`ask`).
- Distribuição de `Herald-Content-Format` servido.
- Taxa de erro (4xx/5xx) por agente.
- Latência agregada por agente.

### 9.2 Privacidade

Métricas agregadas por agente NÃO devem ser confundidas com tracking de usuários finais
humanos. O Herald Protocol não define nem recomenda coleta de dados pessoais de humanos em
nome de quem um agente atua; isso é regido pelas políticas de privacidade já aplicáveis à
origem.

### 9.3 Exposição

O Gateway de referência expõe métricas em formato compatível com Prometheus
(`/metrics`) e alimenta o Dashboard Agent Analytics (ver documento de arquitetura, §5).

## 10. Extensibilidade e Compatibilidade HTTP

### 10.1 Compatibilidade

- Todos os headers Herald são opcionais do ponto de vista de um cliente HTTP genérico:
  a ausência deles resulta no comportamento padrão HTTP/1.1 ou HTTP/2 já existente.
- O Herald Protocol não redefine nem colide com semântica de headers HTTP padrão
  (`Accept`, `Vary`, `Cache-Control`, etc.) — ele os complementa.
- O endpoint `/.well-known/herald` segue a convenção RFC 8615 (Well-Known URIs).

### 10.2 Versionamento

O campo `herald_version` no documento de descoberta segue versionamento semântico
(`MAJOR.MINOR`). Clientes MUST ignorar campos desconhecidos em vez de falhar
(princípio de "tolerant reader").

### 10.3 Extensões

Implementações MAY adicionar headers customizados com prefixo `Herald-Ext-` e campos
adicionais dentro do objeto `extensions` do documento de descoberta. Campos e headers não
reconhecidos MUST ser ignorados silenciosamente por implementações conformes, preservando
compatibilidade futura.

### 10.4 Registro de headers (informativo)

Este RFC define os seguintes headers experimentais (prefixo `Herald-`), candidatos a
registro formal no IANA Message Headers Registry em uma fase posterior:

`Herald-Agent-Id`, `Herald-Agent-Type`, `Herald-Accept-Capabilities`,
`Herald-Content-Format`, `Herald-Policy-Decision`, `Herald-Resource-Policy`.

## 11. Considerações de Segurança

- **Spoofing de identidade**: como `Herald-Agent-Id` é autodeclarado, origens que precisam
  de alta confiança MUST tratá-lo como não verificado a menos que acompanhado de assinatura
  válida (§4.4) ou de correlação com IP/ASN conhecido do agente.
- **Negação de serviço via `/.well-known/herald`**: por ser público e sem autenticação, o
  endpoint SHOULD ser servido a partir de cache/CDN.
- **Uso do Policy Engine como superfície de ataque**: decisões de política não devem
  vazar informação sensível sobre a infraestrutura interna nos headers
  `Herald-Policy-Decision`.
- **Downgrade forçado**: um atacante não deve conseguir, manipulando
  `Herald-Accept-Capabilities`, forçar a origem a expor dados que não estariam disponíveis
  na representação HTML padrão. A regra de §7 (conteúdo não pode variar substantivamente)
  mitiga isso.

## 12. Considerações de Privacidade

Ver §9.2. Adicionalmente, origens que expõem `by_agent_type` ou allowlists nomeadas no
documento de descoberta devem evitar incluir identificadores que exponham relações
comerciais confidenciais (ex. nomes de clientes específicos com acordos de monetização).

## Apêndice A: Exemplo de Fluxo Completo

```
1. Agente → GET /.well-known/herald
   Origem  → 200 OK, application/json (documento de descoberta)

2. Agente → GET /artigos/exemplo
            Herald-Agent-Id: anthropic-claude/1.0
            Herald-Agent-Type: assistant
            Herald-Accept-Capabilities: structured-json;q=1.0, html;q=0.5

   Gateway → consulta Policy Engine: intent=read, agent_type=assistant → allow
   Gateway → seleciona structured-json (maior q suportado por ambos)

   Origem  → 200 OK
             Herald-Content-Format: structured-json
             Herald-Policy-Decision: intent=read; result=allow; rule=by_agent_type.assistant
             Vary: Herald-Agent-Id, Herald-Accept-Capabilities
             Content-Type: application/json
             { ...mesmo conteúdo do artigo, em JSON estruturado... }
```
